# Quick Task 260812-k9m — Phase 9 Plan Fixes (F1..F8)

Docs-only task — no code changes. Applies the review findings from the Phase 9 plan re-evaluation
(context7 + tavily verified) to the planning artifacts so 09-01..09-04 are implementable as written.

## Findings applied

### F1 (CRITICAL, 09-01) — Start button cannot know the selected destination
`START_BTN_ID = 'sanguo:travel:start'` is a static customId; a `ButtonInteraction` carries no
selected value. Context7 verified `StringSelectMenuComponent` (message snapshot) has NO `.values` —
only `StringSelectMenuInteraction` does. **Fix:** encode the destination in the button customId —
`buildStartButton(t, disabled, destinationCode?)` → customId = `${START_BTN_ID}:${code}` when a
destination is selected; `handleDestinationSelect` builds the enabled button with the chosen code;
the router matches `customId.startsWith('sanguo:travel:start')`; `handleStartPress` parses the code
from the customId suffix. Server-side adjacency re-validation (NO_ROUTE) still guards fabricated codes.

### F2 (CRITICAL, 09-03) — `encounterPending` result carries no encounter data
`checkInTravel` returns `{ mode: 'encounterPending' }` with no payload, but the command must re-render
the pending encounter embed (needs hero/zone/encounter_type). **Fix:** when `encounterActive=true`,
fetch the latest `encounter_runs` row (userId + status='pending' ORDER BY id DESC LIMIT 1) and return
it in `CheckInResult.encounter`. The 09-01 encounterRuns schema edit adds an `index('encounter_runs_user_status_idx')`
on (userId, status) so this query is indexed (migration 0018 picks it up).

### F3 (HIGH, 09-01) — startTravel double-start race
Reading the row in a tx without a lock allows two concurrent starts to both see status='arrived' and
UPDATE last-wins (READ COMMITTED; the T-09-03 mitigation as written is wrong). **Fix:** read the
current row with `.for('update')` inside the startTravel transaction (INSERT path still backstopped by
`userId.unique()`).

### F4 (HIGH, CONTEXT/RESEARCH/09-03/STATE) — D-28 "decrements ONLY on failed rolls" vs Pattern 1 code
Pattern 1 / 09-03 decrement the hit minute; D-28 + STATE say only failed-roll minutes count. The code
interpretation is the internally-consistent one (ack-pin `updatedAt + k·60` requires minute k counted).
**Fix:** amend D-28 wording in CONTEXT + RESEARCH to "decrements 60s per counted minute — the minute
whose roll hits IS counted; the loop stops immediately after (no further minutes rolled or counted
until the ack clears the pause)". Align STATE.md paraphrase. Add a clarifying truth + flagged
assumption to 09-03.

### F5 (MEDIUM, 09-03) — sub-minute remainder not banked across an encounter hit
At a hit, only whole counted minutes are credited; the sub-minute remainder (up to 59s) is neither
counted nor banked after ack. Accepted per A5 (per-minute granularity) but undocumented. **Fix:** add
an explicit flagged assumption to 09-03.

### F6 (MEDIUM, 09-01) — zero-adjacent-nodes case untested
`addOptions([])` on a send path can throw NO_OPTIONS; the command must branch to the `no_route` embed
without rendering a menu. **Fix:** explicit empty-adjacent branch in travel.ts execute + a test.

### F7 (MEDIUM, 09-04) — cap ZSET key never expires
`redis:enc:win:{userId}` persists for users who stop checking in. **Fix:** best-effort
`await redis.expire(key, 86400)` after the cap cleanup / ZADD in rollMinute.

### F8 (MEDIUM, 09-04) — hero_zone_rates.rate is numeric → string from Drizzle
`pickEncounterHero` takes `number` rates; DB returns strings. **Fix:** explicit `Number(row.rate)`
conversion when building ZoneRate[] in rollMinute.
